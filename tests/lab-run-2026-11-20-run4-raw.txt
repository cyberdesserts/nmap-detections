  $ echo | openssl s_client -connect 127.0.0.1:<port> -alpn h2,http/1.1
  port 8441 (case 1)  ALPN protocol: h2
  port 8443 (case 3)  ALPN protocol: http/1.1     <- HTTP/2 genuinely off
  port 8449 (case 9)  ALPN protocol: h2           <- h2 IS on

  $ echo | openssl s_client -connect 127.0.0.1:8449 -tls1_2 -alpn h2,http/1.1
  alert protocol version

  Case 9 therefore negotiates h2 but refuses the check's TLS 1.2
  ClientHello, so ALPN is never seen. UNKNOWN is the documented TLS 1.3
  limitation, not a defect.

--- Case 10, two virtual hosts on one port ----------------------------
One container, port 8450, two server blocks: the default with HTTP/2
off, app.example.com with it on. Ground truth first:

  $ echo | openssl s_client -connect 127.0.0.1:8450 -alpn h2,http/1.1
  ALPN protocol: http/1.1                <- the default server block

  $ echo | openssl s_client -connect 127.0.0.1:8450 \
      -servername app.example.com -alpn h2,http/1.1
  ALPN protocol: h2                      <- the named server block

  $ curl -sk https://127.0.0.1:8450/
  case10 default vhost, h2 off

  $ curl -sk --resolve app.example.com:8450:127.0.0.1 \
      https://app.example.com:8450/
  case10 app.example.com, h2 on

app.example.com is an RFC 2606 documentation name and has no DNS
record. It does not need one: NGINX selects the server block from the
TLS server name extension, so the case runs offline and on a CI runner.

Scanned both ways, the check returns opposite answers for the same
address and port, which is cases 10a and 10b in the table above.
